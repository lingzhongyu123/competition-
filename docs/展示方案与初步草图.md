# Memory Console 展示方案与初步草图
日期：2026-10-24；用途：与张旭讨论展示故事、数据和接口。

## 先明确你现在负责什么

当前先做可讨论的展示方案：观众看完后，能解释“一条信息从哪里来、何时发生变化、哪些任务检索到它、是否有记录证明实际使用”。先用草图确认展示内容，再讨论接口；不需要先等完整后端。此前建议直接转向真实接口过早，应先落实本轮内容和典型用例。

## 一、四条展示故事

| 故事 | 观众要理解什么 | 首选数据 | 首屏信息 |
|---|---|---|---|
| 事实记忆 | AI 的事实有来源，不是凭空生成 | LongMemEval single-session-user；偏好另选 single-session-preference | 原始会话、抽取事实、来源时间、适用范围 |
| 信息更新 | 新事实生效，旧事实仍能按时间追溯 | LongMemEval knowledge-update；temporal-reasoning 作为补充 | 更新前后、触发原文、有效区间、问题时间 |
| 任务经验 | 一段操作记录怎样成为带条件的案例 | OSWorld 工时金额计算与产品收入透视汇总 | 任务、环境、动作、产物、验证结果、失败原因 |
| 经验复用 | 检索到经验不等于采用；采用不等于有效 | OSWorld 产品收入透视汇总 → 发票次数统计，作为拟议迁移配对 | 候选经验、适用条件匹配、注入内容、实际动作、结果 |

能力状态：事实/偏好与更新是本轮展示主题，不表示当前系统已经支持其全部语义。Case/Strategy 的生成与复用按后续规划展示，待与后端负责人确认。

## 二、草图 A：事实记忆——先看来源，再看结果

布局：左侧会话列表，中间记忆列表，右侧证据详情。点击事实后，定位原始用户句子，并展示记忆形成记录。

~~~text
┌ 事实记忆     数据来源：LongMemEval / 待导入     题目 ID：待选 ┐
│ 会话与时间         记忆列表                  来源详情       │
│ 会话 1             通勤时长：45 分钟/单程    用户原话       │
│ 会话 2             [查看形成记录]            会话/轮次/时间 │
│                    问：单程通勤要多久？      抽取方式/版本  │
│                    答：45 分钟              证据定位       │
└─────────────────────────────────────────────────────────┘
~~~

上图“45 分钟”仅为 MOCK 文案，不是本次已下载并核实的官方样本。正式替换时必须填写 question_id、会话 ID、时间和原文定位。事实展示与偏好展示要区分：后者说明回答建议如何符合偏好，不能只把事实字段改名。

交互：选择记忆 → 展开原文；选择问题 → 查看实际检索结果。没有系统运行记录时只展示“预期展示路径”，不补造检索命中。

## 三、草图 B：信息更新——用时间滑块解释新旧关系

~~~text
┌ 信息更新     [更新前] ───●─── [更新后]                   ┐
│ 旧事实（历史）       变化原因              当前事实       │
│ 联系地址：A         用户明确说“改为 B”    联系地址：B     │
│ t1 起生效           [展开原文]             t2 起生效      │
│ t2 起失效                                                │
│ 问题时间：t1.5 → 应使用 A；问题时间：t3 → 应使用 B        │
│ 未变化信息：其他独立字段保留                              │
└─────────────────────────────────────────────────────────┘
~~~

地址 A/B 为 MOCK 草图。正式数据优先选 knowledge-update 的同一属性多次变更样本；只有日期/相对时间差异的题目作为 temporal-reasoning 补充，不混作知识覆盖。原始对话并不自带本系统的版本/有效区间字段，这些属于拟议展示模型，需标明系统生成或分析整理。

交互：切换问题时间 → 显示该时刻可见的信息；历史事实可查看但不自动参与当前回答。若两段原文只是不同作用域，显示“并存”而不是自动判为冲突。

不能把任务 JSON 的 trajectory 路径当作已获取轨迹；不能从任务要求推断 Agent 成功。成功案例、失败案例和经验提炼需由真实运行记录支持，未采集前留空或明确标记 MOCK。

## 五、草图 D：经验复用——把迁移边界直接画出来

拟议配对：产品收入汇总任务形成“透视表操作流程”候选，再到发票计数任务展示复用。两者都是官方任务，但这组迁移关系由本方案提出，不是 OSWorld 官方提供的经验链。

~~~text
┌ 经验复用    新任务：发票次数统计                        ┐
│ 1 检索候选        2 适用性检查       3 执行        4 验证 │
│ 透视表流程        同为 Calc          动作引用     产物检查│
│ 来源任务/版本     同需新工作表       或未记录     未运行  │
│                   汇总函数有变化！                       │
│ 可复用：建表流程；需重新选择：Count，不能照搬 Sum         │
└─────────────────────────────────────────────────────────┘
~~~

界面分开显示：召回、选中、实际注入、可观测的执行采用、结果核验。只记录注入时，采用和效果均显示“未知”。不能根据最终成功反推一定使用了某条经验，也不要求显示模型隐藏推理。

复用有效性以后用固定环境、模型和预算的 Memory OFF/ON 对照评估；目标任务答案和评测参考文件不得预先进入经验库。仅这一个配对不能证明总体迁移效果。

## 七、带着草图与张旭确认的最小问题

1. 哪个展示故事最符合当前系统已实现的能力？Case/Strategy 哪些属于规划？
2. 能否先给一条有原始来源的记忆、一条更新记录、一条真实检索/注入记录？JSON 样例即可。
3. 能否给一条真实任务的 run_id、截图、动作、产物和验证结果？没有的字段标“未记录”。
4. DSH 能否承载页面/iframe？这是独立的接入问题，不阻碍先讨论故事。
5. 展示对象主要是竞赛评委、研发还是用户？默认先做面向评委的 3 分钟演示。

初次讨论不需要完整 API。最小反馈成果：确认两条优先故事，标明可给的数据与负责人，约定样例字段。此文档尚未发送给任何人。
