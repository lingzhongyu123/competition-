# Memory Console 演示与接口交接

## 3–5 分钟演示顺序

1. 点击“重置演示”，在 Day 01 记忆总览选中“统一日期格式”。从右侧 Inspector 展开原始用户指令，说明一条指令形成独立的文档事实、排序、日期和修改范围。
2. 切到 Day 03，打开“检索与使用”，选择 trace-d3。依次看候选、注入上下文、合成执行引用。此处的通过结果仅是 MOCK。
3. 切到 Day 07，打开“任务经验”，对比字段映射案例和混合日期失败案例。关注失败原因与适用边界。
4. 切到 Day 10，查看策略候选及来源，再点击新任务注入。trace-d10 有注入、无执行记录，因此页面明确显示无法判定是否采用，更没有收益结论。
5. 切到 Day 14，“更新与管理”显示新旧排序对比，日期格式和修改范围不变。打开右侧变更证据。回到 Day 03 看历史，旧排序仍有效。
6. 回到 Day 14，模拟撤回日期偏好。先看范围预览，可取消；确认后只改变本次演示状态。查看审计中的存储/索引/缓存“未执行”。回到 Day 03，日期仍有效；历史 trace 也不被重写。
7. 打开“数据与评测”，展示公开任务接入情况与未运行的 ON/OFF 表格。导出当前证据包，文件包含 MOCK 声明。

主题按钮切换麒麟概念与中性视觉。事实图谱的箭头表示原始证据 → 记忆 → 模拟注入 trace；虚线表示失效记忆的历史来源，不表示该来源已删除。经验图谱中的 Case/Strategy 来源也是合成事件。

## 给张旭的讨论材料（可直接用于会议，尚未发送）

Console 的首轮目标是只读可观测性。希望先拿到以下脱敏数据与契约：

| 数据 | 最小字段 | 页面用途 |
|---|---|---|
| 记忆列表/详情 | memory_id、workspace_id、kind、content、scope、status、version | 列表和 Inspector |
| 时间更新 | valid_from/to、recorded_at、supersedes、更新原因 | 当前与历史视图、新旧对照 |
| 原始证据 | evidence_id、session_id、event_id、role、时间、原文或脱敏原文 | 追溯事实来源 |
| 检索轨迹 | trace_id、query、候选与排除原因、selected_ids、injected_ids | 区分召回与实际注入 |
| 执行引用 | run_id、动作事件、实际使用引用、产物与检查记录 | 不把注入误认为采用 |
| 案例/策略 | Case 的环境、动作、结果；Strategy 的案例来源、条件与反例 | 规划能力上线后接入 |
| 管理能力 | 只读/撤回/删除能力、权限、幂等与任务状态 | 控制可用入口，验证实际完成范围 |

附件中 `memory_search` / `memory_write` / `memory_forget` 是主动工具名称，不能据此假设已经有同名 HTTP API。请优先确认真实签名和返回例，再决定适配层。

首轮可以只给：一组来源完整的事实/偏好、一组同作用域的新旧规则、一条含实际注入字段的 trace。没有字段就显示“未记录”，不要通过最终输出反向补造使用证据。

## 代码接入边界

当前页面的数据来自 `createMockProvider()`。`getSnapshot(day)` 返回模拟时间点的记忆、证据、事件、trace 和 capabilities。模拟撤回仅在 Day 14 允许，全部状态只存在内存。换成真实来源时建议新增独立 provider/控制器，不修改 mock 原始数据：

- 模式应显式选择并显示来源，页面不可从线上错误静默切回 MOCK。
- 真正的异步 API 必须处理 loading、error、empty、unauthorized、unsupported；不能将空数组当成所有状态。
- workspace_id 仅用于选择；服务端必须独立鉴权与隔离工作区。
- snapshot 或历史接口需确认是否按事件时间还是记录时间重建；原型 day 只是故事标号，不是正式时间格式。
- 使用带时区 ISO 8601 时间；日期格式偏好中的 YYYY-MM-DD 是业务产物格式，两者不同。
- status、validity 与删除范围由后端保证。真实 forget 要有独立授权、并发版本检查、幂等键与完成状态；现有模拟撤回函数不能直接绑定生产删除。
- 检索 trace 是发生时的历史事实，后来的更新不能改写它。
- 任务定义与评测参考数据分开。公开任务卡片不含初始化脚本、evaluator 期望答案或参考文件。

## DSH 技术路径

当前用户尚未拿到 DSH 仓库资料；没有完成任何 DSH 兼容性验证。独立 Console 已可运行，但它并不证明 DSH 能托管页面插件。

| 条件 | 推荐路径 | 必须验证 |
|---|---|---|
| 支持前端页面插件 | 将 Console 挂载到宿主菜单与页面容器 | 路由、生命周期、资源基址、主题 token、权限 |
| 只支持内嵌页面 | 同源托管或受支持的 iframe 页面 | frame-ancestors / frame-src、登录、资源路径、通信来源 |
| 可维护前端源码 | 新增路由入口与样式作用域 | 版本维护与发布成本，不称为原生插件 |
| 无页面扩展且不能改宿主 | 保留独立 Console | 直接在 DSH 前端打开的目标暂不能达成 |

当前 CSS 只为独立页面设计，尚未封装为原生插件组件。未来若直接注入宿主 DOM，须先限定样式作用域、移除 body/global 选择器与全局 hash 路由依赖；若用 iframe，优先隔离样式。宿主给出工作区与主题时使用正式协议；postMessage 校验 origin、source 和消息结构，不在 URL 中携带令牌。

麒麟风格分两层：Console 内的配色、中文和桌面式信息层级可以独立完成；DSH 全局主题要核实其扩展能力。当前主题切换仅影响 Console，没有修改 DSH。
