# Memory Console 在 DSH 前端打开：可行性核查

## 2026-10-26 本机实际挂载结果

在隔离的 DSH 0.2.1-rc.2 Web profile 中安装 `dsh-advanced-mem-plugin` 0.3.0 和本仓库的 `memory-console-dsh` 伴随插件。后者通过官方 `main` 与 `sidebar.panellist` 插槽增加侧栏入口，并在受限 `srcDoc` iframe 打开单文件演示。浏览器实测入口可点、页面可见、麒麟蓝灰配色开关可开启并恢复，页面脚本错误为零。[界面截图](images/Memory-Console-DSH-插件预览.png)。

iframe 不具备同源权限；这是演示挂载，不代表 Console 页面已读取 DSH/Memory 的实时数据。DSH 原生 Memory 插件在两条合成模型任务中自动保存了事实偏好；新会话轨迹可见该偏好被检索并注入，上下文与回答一致。经验 episode 有 2 条但技能为 0，尚未验证经验复用或效果收益。当前主题只覆盖经 DSH `theme.overrideTokens()` 支持的颜色 token，按钮关闭或卸载伴随插件时释放覆盖；它不是麒麟官方主题，也不修改团队仓库的 DSH 源码。固定版本和可复现构建见 [插件说明](../plugins/memory-console-dsh/README.md)。

后续已在无 `/dev/kvm` 的本机 Docker 中运行 OSWorld 官方 Ubuntu 虚拟机和工时任务，取得一次未触碰基线及两次失败动作的官方评分，均为 0.0。DSH 模型仅根据转写的屏幕文字建议公式，OSWorld 动作由外部操作分别执行；没有建立 DSH Agent 自动控制 OSWorld 的链路，也没有记忆 ON/OFF 收益。详见[本机运行记录](OSWorld-本机运行记录.md)。此边界与上面的页面挂载验证分开。

## 已取得的事实

- 当前仓库是独立 Web 原型；根目录 `双击打开演示.html` 是含样式、数据和脚本的单文件。另有本地 HTTP 入口。插件源码及声明兼容的 DSH 版本已核对；尚无团队实际宿主运行环境及登录/CSP 配置。
- Console 当前直接写入 `#app`，使用 `document.body` 设置模式和主题，读取/修改当前窗口的 hash 路由，基础 CSS 有 `body` 等全局选择器。因此不能把现有脚本和 CSS 原样注入 DSH DOM，就宣称是原生插件。
- 本地创建一个普通同源宿主页，通过 iframe 加载根目录演示；浏览器中两条 OSWorld 故事能切换，iframe 内 URL 从 `#osworld?story=reuse` 变为 `#osworld?story=formation`，宿主页地址不变。这只验证浏览器嵌入方式，**没有验证 DSH 本身**。

## 目前的判断

| 路径 | 当前判断 | 在实际宿主中仍需验证 |
|---|---|---|
| DSH 提供前端插件/页面扩展接口 | 本机固定版本已通过 `main` 和 `sidebar.panellist` 挂载 Console 页面 | 团队实际部署版本、维护方式和数据授权边界 |
| DSH 允许宿主页面嵌入 iframe | 本机固定版本的 `srcDoc` 受限 iframe 可用 | 团队部署的 CSP、反向代理和真实数据通信协议 |
| DSH 前端源码可改 | 已找到官方仓库；团队分支与维护权限待确认 | 所用框架、构建与发布方式、导航入口、页面容器及升级维护责任 |
| DSH 不提供扩展也不可改 | 继续用独立 Console | 能否从 DSH 菜单打开外部页面，由负责人确认 |

本机版本已证明可以用插件增加独立页面。若要读取实时记忆，仍需定义宿主只读接口、工作区权限及数据契约；当前 iframe 没有与宿主进行消息通信。团队部署方式和长期维护入口需要继续联调确认。

## 麒麟风格的范围

当前 Console 已有浅色标题栏、浅灰侧栏、蓝色选中态，是受麒麟公开视觉启发的概念样式。本机 DSH 伴随插件还提供可切换的蓝灰 token 覆盖，让宿主侧栏与工作区一起预览；关闭开关会恢复原主题。若要形成正式 DSH 主题，仍需设计审核、更多页面验证和团队发布安排。它不是麒麟官方 UI 规范或官方主题。

## 向张旭确认的最小信息

1. 实际部署是否采用已核对的 DSH 0.2.1-rc.2 和插件 0.3.0，还是其他分支？能否提供隔离的开发 profile 与一份脱敏数据？
2. 已有 plugins.bundle.config 配置页；Console 应沿此入口试验还是另开菜单页？所选入口的生命周期、静态资源和只读鉴权契约是什么？
3. 若插件不可用，是否允许同源 iframe 或新路由？现有 CSP、登录方式和反向代理路径有哪些限制？
4. 外部页面能否取得当前 workspace ID、用户可见权限和主题配置？可用的正式协议是什么？
5. “更麒麟风味”是指 Console 页面，还是 DSH 的导航与其他页面？谁负责最终视觉审核和发布？

拿到实际运行环境与所选入口契约后，可以在 DSH 开发环境做一条最小验证：从受支持的入口打开 Console，切换两条故事，刷新和返回不破坏宿主路由，主题与权限保持一致。成功后再决定是否重构为原生插件。
